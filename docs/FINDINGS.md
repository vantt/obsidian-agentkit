# Findings: Obsidian CLI measured on this setup

Phase 1 of `docs/handoff/BUILD-PROMPT.md`. Every item: command, short output excerpt (redacted), environment, verdict.

- **Date:** 2026-10-22
- **Obsidian:** `obsidian version` → `1.14.4 (installer 1.14.4)`; the app and CLI report the same version.
- **Host:** Windows 11, Obsidian installed per-user at `C:\Users\<user>\AppData\Local\Programs\Obsidian\` (`Obsidian.exe` and `Obsidian.com` side by side).
- **Environments:** WSL2 (Linux 5.15, via interop), Windows PowerShell 5.1 (`powershell.exe`), Git for Windows bash (`bash.exe -lc`). PowerShell and Git Bash were started from WSL as Windows processes; no admin shell was tested.
- **Vault under test:** `vault-copy` at `C:\obsidian-agentkit-test\vault-copy`, a full copy of the real vault (about 1,845 notes, 3 GB), git-tracked for text files only. Synthetic cases live in `_agentkit-lab/`, generated by `tests/fixtures/gen-fixture.mjs`. The real vault was only read (counted and copied), never written.
- **Ground truth:** `tests/ground-truth/gt.mjs`, which uses files only. It now lives on, with the same output, as `otf truth` in [`obsidian-test-fixture`](https://github.com/vantt/obsidian-test-fixture).

## F1 Reachability

| Env | Invocation that works | Verdict |
|---|---|---|
| WSL | `cd /mnt/c && /mnt/c/Users/<user>/AppData/Local/Programs/Obsidian/Obsidian.com vault=vault-copy …` (no `obsidian` on PATH) | confirmed |
| PowerShell | `obsidian vault=vault-copy …` (`Get-Command obsidian -All` lists `.com` first) | confirmed |
| Git Bash | `obsidian.com vault=vault-copy …` | confirmed |
| Git Bash | `obsidian …` resolves to `Obsidian.exe`: plain commands work (with a leading blank line), colon commands exit **127** with no output (`property:read …` → `exit=127`) | confirmed (lesson `windows-com-redirector-and-wrapper`) |
| Admin terminal | not tested (would need elevation) | could not test |

- **F1a Obsidian closed.** In all three environments, `version` prints `The CLI is unable to find Obsidian. Please make sure Obsidian is running and try again.` and exits **1**. From WSL interop this message arrives on **stderr** with empty stdout (seen when the app was closed during a later run); in PowerShell it showed on the console stream. It takes about 144 ms, does not hang, and does not start Obsidian. Verdict: confirmed. One call is enough to detect it.
- **F1b App starting up or reloading.** For a few seconds, commands fail with `Error: Command "vault" not found. Did you mean: daily?` or `Error: Command "eval" not found. It may require a plugin to be enabled.`, still exit 0. `vault info=name` can succeed before every command is registered. Verdict: confirmed. The bridge must treat "Command … not found" during the first seconds as "not ready".
- **F1c Vault targeting.** `vault=<name>` must be the first argument. `version vault=vault-copy` and `vault info=name vault=no-such-vault` both ignored the param and answered for the focused vault. A wrong name in the first position prints `Vault not found.` with exit 0 and no `Error:` prefix. Verdict: confirmed (lesson `vault-targeting-first-param`).
- **F1d Interop cwd.** Run from a `/mnt/c` cwd so the Windows process gets a drive-letter working directory.

## F3 Paths

- The CLI prints **vault-relative paths with forward slashes** (`_agentkit-lab/tiếng việt/Ghi chú tiếng Việt.md`) in `search`, `backlinks`, `tasks` and `file`. `path=` takes the same form.
- `vault info=path` prints the Windows absolute path `C:\obsidian-agentkit-test\vault-copy`, without a trailing CR.
- `wslpath -u 'C:\…'` and `wslpath -w` round-trip correctly with spaces and Vietnamese diacritics. Strings were NFC on both sides, and joining the vault path with a CLI-relative path gives a file that `ls` finds. Verdict: confirmed, `wslpath` is enough.

## F4 `move` and `rename` with link updates

Lab target with 9 referrers: wikilink, `|display` link, heading, block, embed, `%20` markdown link, another folder, Vietnamese file name, and a frontmatter list. A code-block link and an alias-name link (`[[TN Alias]]`) were placed as decoys.

- **F4a `alwaysUpdateLinks: true`.** `rename path="_agentkit-lab/Target Note.md" name="Target Renamed"` printed `Renamed: … -> …`. All 9 referrers were rewritten (`git diff`), `backlinks … total` stayed at 9, and `unresolved total` stayed at 87. The code-block link was untouched. `move … to=_agentkit-lab/moved/` behaved the same way. Verdict: confirmed, links are updated.
- **F4b Markdown links are restyled.** `[target](../../Target%20Note.md)` became `[target](Target%20Renamed.md)`, the `shortest` form from `newLinkFormat`. The link still resolves, but its style and path changed. Verdict: confirmed.
- **F4c `alwaysUpdateLinks: false`.** Obsidian opens a modal that reads *"Update links. Do you want to update internal links that link to this file? This will affect 9 links in 9 files. [Always update] [Just once] [Do not update]"*. The **CLI blocks until a person answers**. With no answer, the 10 s timeout fired (`exit=124`), but the file **had already been renamed** and the links were not updated (`unresolved` went from 87 to 89). Clicking "Do not update" let the CLI return `Renamed: …` with exit 0 and broken links. During one run, someone at the screen clicked "Always update", which turned the setting back on. Verdict: refutes the YARDSTICK assumption "move/rename update links regardless of the setting".
- **F4d `move` into a missing folder.** It prints `Error: ENOENT: no such file or directory, rename '…' -> '…'` with exit 0, and nothing moves.
- **F4e `backlinks` resolves** every form except the alias-name link. `[[TN Alias]]` is listed by `unresolved` as an unresolved target, because Obsidian does not resolve links by alias.

## F5 `delete`

- With the default `trashOption` `system` (the key is absent from `app.json`), `delete path=…` prints `Moved to trash: …` and the file lands in the **Windows Recycle Bin** (`Shell.Application` namespace 10 lists it, `DeletedFrom C:\obsidian-agentkit-test\vault-copy\…`). No `.trash/` folder is created.
- With `trashOption: "local"` set through `app.json` + `reload` (`getConfig` → `local`), and again through `setConfig`, CLI `delete` **still went to the Recycle Bin**: 3 copies in the bin, and still no `.trash/`. Verdict: the CLI ignores the vault trash setting.
- `permanent` exists (`delete … permanent — Skip trash, delete permanently`). It was not run.
- Missing file: `Error: File "…" not found.`, exit 0.
- Google Drive (2026-10-28, CLI 1.15.0, test vault in a folder under `G:\My Drive`, `trashOption` `system`): CLI `delete` printed `Moved to trash: …` and the file landed in the **Windows Recycle Bin**, `DeletedFrom G:\My Drive\…\refs`, the same as on `C:`. So it is restorable from the local bin. Bridge `--trash` moved the file to the vault's `.trash/` instead, which Drive syncs like any folder. Whether Drive's own web Trash also keeps a copy is checked by the user on drive.google.com.

## F8 Source conflicts resolved

- **F8a `search format=json matches`.** `matches` is ignored, and the output is a path array. Line-numbered matches come from **`search:context … format=json`**: `[{"file":…,"matches":[{"line":9,"text":"## Section A"}]}]`, with 1-based lines. Pablo was right for 1.14.4.
- **F8b Plain `tasks`.** It covers the whole vault, even with a file open (`open path=…tasks-1.md`, then `tasks total` → 147, the same as ground truth; `tasks active total` → 3). Pablo was right; jackal's 1.12 behaviour no longer applies.
- **F8c Token traps found while testing.** An unquoted multi-word query matches each word separately, so `query=Section A` hits 4 files. On top of that, `search:context` repeats a line once for every term that matches it, and printed **410 KB** for those 4 files. Quoted, `query='"Section A"'` returned 2 files and 254 bytes. `search … total` counts **files**, not matches. Search is case-insensitive and diacritics-sensitive (`Da Nang` ≠ `Đà Nẵng`).

## F9 Single-source traps

- **F9a `property:set` and lists** (`property-set-list-trap`).
  - `value="proj, newtag"` with no type writes the string `tags: proj, newtag`.
  - With `type=list`, plain words become a YAML list, but `value="[[A]], [[B]]" type=list` stays the single string `"[[A]], [[B]]"`.
  - A JSON array `value='["[[A]]","[[B]]"]'` becomes a proper list, with or without `type`.
  - A number without `type=number` becomes a string (`rating: "5"`).
  - Verdict: confirmed, and worse than the source says.
- **F9b `property:set` changes `types.json` for the whole vault.** Setting `tags` from a JSON array changed `"tags": "tags"` to `"tags": "multitext"`. `type=…` also registers new keys (`rating: number`, `done: checkbox`). Plain text values on new keys did not register anything. Verdict: new finding, and convention corruption (failure mode 5).
- **F9c `create`.**
  - It makes parent folders (F7).
  - **`create` on an existing path silently creates `name 1.md`**: `Created: _agentkit-lab/created-plain 1.md`, exit 0, and the original is untouched.
  - `name=` with no path goes to the vault root, following `newFileLocation`.
  - `\n` in `content=` becomes LF.
- **F9d `properties format=json` returns JSON** (F7 S3) (`output-format-quirks` refuted for 1.14.4).
- **F9e UI side effects.** `create`, `append`, `daily:append` and `property:set` opened no tab. Only `open` and the `open`/`newtab` flags do. `silent` is not in help and is ignored.
- **F9f `total`.** It works on `files`, `folders`, `tags`, `tasks`, `backlinks`, `links`, `orphans`, `deadends`, `unresolved`, `aliases`, `properties`, `outline`, `search` (files), `templates` and `recents`. It is **ignored** by `search:context` and `bases`, which then print the full list (`count-first-total-flag` partly confirmed).
- **F9g `daily:*`.**
  - `daily:path` → `2026-10-22.md` with the defaults.
  - With `daily-notes.json` set (`folder`, `format: YYYY/MM/YYYY-MM-DD`, `template`), `daily:append` created `_agentkit-lab/daily/2026/10/2026-10-22.md` from the template, making the `YYYY/MM` subfolders. The **root daily folder must already exist**; otherwise you get `Error: Folder "…" not found.` / `Error: Failed to open daily note.` with exit 0.
  - **A rerun appends again**, so duplicates are possible.
  - `daily:prepend` inserts at the top of the body.
  - No UI side effects.
- **F9h `outline`.** `format=json` gives `{"level","heading","line"}` with 1-based lines, which feed straight into a ranged read (`Read offset=…`). `total` → 31 headings for the 2,974-line CRLF note.
- **F9i `tag name=proj verbose`** counts nested `#proj/sub` too (5 occurrences, where ground truth for exact `#proj` is 2 in body + 2 in frontmatter). It does not count `#projects` or code blocks.

- **F9j `daily:read` creates the note (found in Phase 4, 2026-10-22).** With no daily note on disk, `daily:read` printed nothing (bridge exit 4), and right afterwards `2026-10-22.md` existed with 0 bytes. A read command has a write side effect. A later `daily:append` into that empty file starts the note with a blank line (`\n- [ ] …`). Verdict: new finding. The skill checks with `daily:path` and file tools instead.
  - **Re-checked on CLI 1.15.0 (2026-10-28), `vault-synth`:** still true. That vault's Daily notes setting has a template (`Templates/Daily`), so the note `daily:read` creates holds the rendered template, not 0 bytes. The side effect is the same. Probe P29 now passes on "the note exists afterwards" and records its size.
